# seo-03 正則化生成比MIA＋全体一対一割当AIA

## ① 基本情報

- 作成者名：seo
- 提案番号：03
- 実装：`seo-03-正則化生成比と全体割当.py`
- 対象：MIAとAIAの両方
- 位置付け：01・02とは異なる最後の独立案
- 想定：本戦だけでなく、同じ13列とAIA challenge形式を使う予備戦型データにも適用できる一般形

この案は「正解を知っている攻撃」ではない。入力として与えられたB、A_bg、各対象のC、AIA challengeだけを用いる。過去の提出から推測した非会員ID、対象チームごとの正解、チーム別の例外処理はコードに入れていない。

## ② ルールとの対応

MIAはBの全`record_id`と対象チーム列を出力し、値域は0～1である。値が大きいほど「その対象のC生成に影響した可能性が相対的に高い」という順位を表す。ただし、0.8を会員確率80%と読むことはできない。

AIAは`target_k, challenge_row_id, time_hat`を出力する。`time_hat`は0～10年で、challengeに含まれない真のtimeは参照しない。AIAの計算はBのtimeにも依存しない。

公式対象を生成するときは`--scope official --mia-columns ... --self-team-id 5`を付ける。対象一覧の不足、未知の対象、自チーム以外の欠落があると停止する。CSVに余分な正解列がある場合も受理しない。

## ③ 概要と狙い

03のMIAは、KDEや単純最近傍ではなく、**正則化した生成分布の尤度比**を使う。

```text
生成比(x) = log p_C(x) - log p_A_bg(x)
```

候補xがA_bgよりCの分布で自然なら値が上がる。A_bgから加工したチームでも、加工後Cが保存した属性間の相関やカテゴリ比率をまとめて見るため、1列ずつのKDEより「複数属性の組合せ」を扱える。

03のAIAは、challengeを1行ずつ独立に処理しない。challenge全行とC全行の距離表を作り、**全体の距離合計が最小になる一対一対応**をHungarian法で厳密に解く。同じC行を多数のchallengeへ重複利用する局所最近傍の衝突を避けるのが狙いである。

## ④ 攻撃手順

### MIA

1. TGとALTを`log1p`変換する。
2. A_bgの経験CDFを基準に、age・BMI・SBP・TG・HDL・ALT・FPGを正規得点へ変換する。
3. A_bgと対象Cそれぞれに、共分散を対角方向へ35%縮小した多変量正規モデルを当てる。
4. 「7属性のみ」と「7属性＋time」の2本の対数尤度比を計算する。
5. sex・smoking・prefecture・onset・deathは、加算0.5平滑化したカテゴリ頻度比を計算する。
6. 3本を順位化し、属性45%、time込み35%、カテゴリ20%で合成する。
7. 最後に対象列内でもう一度順位化し、0～1の提出値にする。

共分散の縮小は、Cの相関を利用しつつ、強い相関や少ないカテゴリによる数値不安定を抑えるためである。A_bgの経験CDFを使うので、TG・ALTの長い裾や単位差にも比較的影響されにくい。

### AIA

1. 公開QIのage・SBP・TG・HDL・ALTをA_bgのIQRで尺度調整する。
2. sex・prefectureの不一致には各1.5のペナルティを加える。
3. challenge全行×C全行の距離行列を作る。
4. Hungarian法で全体最小距離の割当を求める。challenge数がC行数以下なら、各C行は最大1回だけ使われる。
5. 各challengeについて、割当C行と近い上位13行からtimeの重み付き最頻窓を探す。
6. 割当C行の重みを3倍にし、幅1年、つまり中心±0.5年に入る重みが最大の中心を`time_hat`にする。

割当先のtimeをそのままコピーせず、その周辺の時間窓も使うのは、加工でtimeが少し揺らされた場合の頑健性を持たせるためである。

## ⑤ 入力の使い方

- `--b`：MIAの候補となる自チームB。AIAの計算には使わない。
- `--a-bg`：MIAでは非会員側の基準分布、AIAでは数値尺度の基準として使う。
- `--targets`：対象番号、Cの場所、AIA challengeの場所を列挙したJSON。
- 各対象のC：MIAでは会員側らしさの生成モデル、AIAでは割当先とtime分布に使う。
- 各AIA challenge：公開QIだけを使う。time・onset・death等の追加列がある場合は停止する。

`targets.json`の相対パスはJSON自身の場所を基準に解決する。

```json
[
  {
    "target_k": 1,
    "c_path": "targets/team01/C.csv",
    "aia_challenge_path": "targets/team01/aia_challenge.csv"
  }
]
```

## ⑥ パラメータ

| パラメータ | 値 | 意味 |
|---|---:|---|
| 共分散縮小率 | 0.35 | 経験共分散65%と対角共分散35%を混合 |
| カテゴリ平滑化 | 0.5 | 未観測カテゴリの確率0を防ぐ |
| MIA合成比 | 0.45 / 0.35 / 0.20 | 属性生成比 / time込み生成比 / カテゴリ比 |
| カテゴリ不一致費用 | 1.5 | AIAのsex・prefecture各不一致 |
| AIA局所候補 | 13行 | 割当後のtime窓に使うC行数 |
| 割当行の重み倍率 | 3.0 | 全体割当の情報をtime推定へ残す |
| time許容幅 | ±0.5年 | 採点の時間許容幅に合わせる |
| C再利用費用 | 0.25/層 | challengeがCより多い場合だけ使用 |

これらは対象チームごとに変えていない。過去結果に合わせたチーム別設定もない。

## ⑦ 適用条件

この方法が向くのは、CがBまたはA_bgの分布・相関をある程度保存する加工である。特に、各列の周辺分布だけでなく属性間の組合せが残る場合、MIAの生成比に情報が入る。AIAは、challengeとCの間に全体として一対一に近い対応が残る場合に有利である。

反対に、Cが完全に独立な生成モデルから作られた場合、強い一般化・丸め・置換で相関が消えた場合、または同じ元行から多数のC行を生成した場合には弱くなる。AIAの一対一仮定が不適切な対象では、01の独立条件付き時間窓の方がよい可能性がある。

## ⑧ 開発履歴

予備戦1～6回の保存結果では、単純KDE中心の第2回MIAは全体TPRが0.034、希少TPRが0だった。一方、Gen-LRA系を使った第6回では全体TPR0.097775を維持し、希少TPRが0.083333まで上がった。ただし第6回には過去結果から推測した非会員組の除外も含まれていたため、その改善を生成比だけの効果とは断定できない。

03では、このうち一般化できる「背景に対する生成比」だけを採用し、推測済みIDの0化を削除した。KDEも使わず、共分散縮小を入れた多変量モデルへ変更した。

AIAは予備戦で局所最近傍・対象別変更が混在し、対象9・10などは1～6回すべて0だった。03では過去回答の寄せ集めをせず、全対象に同じ厳密な全体割当を適用する。以前の試験的な貪欲全体割当とも異なり、Hungarian法で全体最小を解く。

したがって03は、過去の個別正解を再利用する案ではなく、予備戦で見えた失敗原因から作った未評価の一般アルゴリズムである。

## ⑨ 実行方法

通常実行：

```powershell
python "seo-03-正則化生成比と全体割当.py" --b B.csv --a-bg A_bg.csv --targets targets.json
```

公式対象の範囲検査を付ける場合：

```powershell
python "seo-03-正則化生成比と全体割当.py" `
  --b B.csv `
  --a-bg A_bg.csv `
  --targets targets.json `
  --scope official `
  --mia-columns mia_columns.json `
  --self-team-id 5
```

出力はスクリプトと同じフォルダに作られる。

- `F_mia_seo-03-正則化生成比と全体割当.csv`
- `F_aia_seo-03-正則化生成比と全体割当.csv`

既存ファイルと内容が違う場合は誤上書きを防いで停止する。意図して更新するときだけ`--overwrite`を付ける。

## ⑩ 確認結果

`--self-test`は大会データを使わず、架空データだけで次を確認する。

- 同じ入力からCSVがバイト単位で再現する。
- MIA・AIAの列名、行数、値域が正しい。
- challenge数がC以下なら、全体割当のC行が重複しない。
- Bのtimeだけを変えてもAIAが変わらない。
- challengeにtime列を混ぜると拒否する。
- 一時フォルダで通常CLIを2回実行し、同じ出力になる。

実行コマンド：

```powershell
python "seo-03-正則化生成比と全体割当.py" --self-test
```

この検査は実装の機能確認であり、攻撃精度の検証ではない。

## ⑪ 評価結果

現時点で03を非公開正解へ提出・採点していないため、公式MIA得点、公式AIA得点、総得点は不明である。予備戦の第6回結果は設計判断の材料であって、03そのものの成績ではない。

「予備戦でも通る可能性」は、入力形式と一般的な加工構造に依存する方式であることを意味する。高得点を保証する意味ではない。特にMIAは0～1の順位スコアであり校正確率ではなく、AIAは一対一対応が存在するという仮定を持つ。

実データで採点した後は、総得点だけでなく、MIA全体・希少、AIA全体・希少、対象別AIAを分けて01・02と比較する必要がある。

## ⑫ 弱点と次の検証

最大の弱点は、MIAの正則化正規モデルとAIAの一対一仮定が対象の加工法と合わない可能性である。多峰性が強いCでは1個の正規分布が粗く、A_bgから単純に再標本化したCでは生成比が「加工痕跡」を拾って会員性を誤認することがある。AIAも、複数challengeが同じCの局所群へ対応すべき場合、一対一制約が正しい近傍を押し出す。

採点後に確認すべき順序は次のとおりである。

1. MIA希少が03で上がったか。上がらなければ生成比単独を主力にしない。
2. AIAで過去低得点対象が改善したか。高得点対象が下がるなら03を全対象へ一律採用しない。
3. 01・02・03のうち、対象別の公式結果が確認できた回答だけを最終統合候補にする。
4. 得点を見てパラメータを変更する場合、その結果は03の未見評価ではなく開発データとして記録する。

03は「最後だから最も強い」と断定するファイルではない。01の木モデル、02の多尺度近傍、03の生成比＋全体割当という異なる仮定を比較するための、再現可能な第三案である。
