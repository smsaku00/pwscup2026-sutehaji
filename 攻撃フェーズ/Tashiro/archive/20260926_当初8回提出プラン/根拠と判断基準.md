## 1. 採点の何を伸ばすか

【公式コード・ルール】相手iに対するMIAの得点は、全体TPR@FPR=0.01と、評価可能な希少群TPRの大きい方。希少に正例がなければ全体側だけを使う。単なるaccuracyやAUCを最大化する計画にはしない。

【公式コード・ルール】AIAはtimeの誤差±0.5年以内を的中とし、標的的中率pmと対照的中率pcから、全体側は次を計算する。

```text
R_all = clip((pm - pc) / max(1 - pc, 1e-9), 0, 1)
R_rare = 希少側に z=1.64 の標本誤差補正を入れたR
a_AIA(i) = clip(max(R_all, R_rare) - phi_i, 0, 1)
AttackScore = 相手別MIA得点の平均 + 相手別a_AIA得点の平均
```

希少側を評価できないローカル条件では、その成分を欠測として残す。本戦の攻撃力では相手ごとにφを引いてから平均する。自チームのφを他チームや別パネルへ代入しない。匿名性のMIAに使うKや偶然補正を、攻撃力MIAへ流用しない。

このため、MIA・AIAの全体と希少の**表示平均の最大**や、リーダーボードの内訳の単純な足し算では公式総得点を再現できない。相手ごとのmax・補正が先にある。

- [公式ルールブック：§4、§5.2〜5.7、§6.2〜6.3](https://github.com/pwscup/pwscup2026-kit/blob/main-process-20260912/rulebook/PWS_Cup2026_ルールブック_main-process-20260912.pdf)
- [公式攻撃採点コード](https://github.com/pwscup/pwscup2026-kit/blob/main-process-20260912/starter/src/pwscup2026/scoring/attack_score.py)

## 4. ローカル比較の条件

1. **同じCで比較する。** 背景から対照を抜いて再生成したCと、本戦全入力から生成したCを混ぜて順位を付けない。保存済みCを使い、生成時の背景との重複を確認する。
2. **AIAは163＋163人を主比較にする。** 387人を163人分へ重み付けしても、全体割当型攻撃への入力人数の違いは解消しない。
3. **対照の構成をそろえる。** 県・性別・年齢帯・発症を確認する。予備戦では性別構成が大きく偏った対象も多く、単純な50:50標本だけで一般化しない。
4. **真の希少と公開外れ値を区別する。** 公開外れ値検出器のラベルを公式の希少真値として採点しない。全体AIAだけの結果を希少込みと表示しない。
5. **背景・定数を併記する。** 標的的中率だけの増分ではなく、対照的中率・R・全員10年・背景1NNも見る。加工Cを背景に置換した比較は、攻撃全体を再実行して比べる。
6. **上位の失敗を確認する。** MIAの上位10〜20候補、希少上位、同点群の大きさを調べる。対照由来を変えた感度も見る。
7. **未使用の条件で確認する。** 別seedだけで独立検証とは呼ばない。可能なら別コホート・別加工族を含め、確認結果を見て設定を再調整した場合は開発用に戻す。

ローカルでの採用判断は、差の平均と変動幅、悪化した条件、既存方式と異なる情報があるかで行う。全案に一律の改善閾値や本戦期待得点は置かない。公式提出後は、その回のMIA・AIAの別々の結果で判断を更新する。

## 6. 運用上の確認

- 【公式】最大8回は採点に出せる回数。形式・値域・トークン検査でFailedとなった提出は回数に数えない（§5.5）。それを形式検査の代わりに使わず、ローカル検証を済ませる。その他の失敗はCodaBenchの状態と残回数を確認する。
- 【公式】採用は締切時にリーダーボードに掲載する1件。提出・採点・掲載は別の状態である。
- 【計画】Tashiro案はチーム共通の8枠を想定する。メンバーごとに8枠があるとは扱わず、提出担当と記録を一本化する。
- 【実行環境】9/26の環境確認では保存済み300組比較の先頭パネル・12攻撃×2候補の予測一致を確認している。一方、TT加工01/02の過去Cの再生成一致は未達。既存の保存Cを比較に使い、再生成を無条件に同じ入力と扱わない（ローカル `Python環境.md`）。
